# Build the Lance search sidecar in staging while parsing shards

The Linux reset benchmark in docs/tasks/profile-linux-corpus-index-time-and-storage.md reduced search-build from 606.82s to 224.55s and exposed 122.92s of row/document preparation plus 43.65s of Lance writes before the 57.97s index-build tail. Parse itself takes 151.92s. Prepare file/entity rows into a generation-scoped staging Lance store through a bounded channel as parse results become durable, then build FTS/scalar indexes and publish only after parse/cache/graph success. Never mutate the active search tables during parse: failure or a newer corpus generation must discard staging, and graph/search/source publication must remain coherent. Reuse the existing pending/ready generation protocol and preserve source retrieval. Acceptance: Linux wall time overlaps most of search prepare/write with parse, peak memory remains bounded, a failed parse/build leaves the prior sidecar queryable, and full/incremental/search/source tests pass.
