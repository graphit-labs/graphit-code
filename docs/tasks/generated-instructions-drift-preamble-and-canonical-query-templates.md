# Generated instructions in drift — the mandate preamble does not propagate and the AST skill's query templates are refused by the planner

## Objective

Two independent defects, both in the category "generated text that instructs agents is
wrong and nobody notices", found from a single symptom reported by the user:
`graphit sync` does not update `AGENTS.md` with changes to `mandatePreamble`, even with the
installed binary up to date.

**Defect 1 — the preamble is never compared.** `UpsertMandateTrigger`
(`internal/hub/adapters/ide/mandate.go`) decides whether to rewrite the file by comparing only
each module's `triggerContent`. `mandatePreamble()` takes part in assembling the block but takes
no part in any freshness comparison. Consequence: changing only the preamble never triggers
a rewrite, and `AGENTS.md` keeps the old text indefinitely.

**Defect 2 — the `graphit-ast` skill teaches queries the engine itself refuses.** The text is
generated by `internal/ast/rule.go`. It documents the `canonical catalog: ...` refusal in one
section (lines 387-406) and then delivers ~96 traversal templates, the vast
majority of which violate the rules it has just stated. The query I ran myself in this session
and that errored out came from the block marked `🔒 MANDATORY: Before You Edit` (line 83).

**Defect 3, found during the investigation — `ORDER BY` is broken in the planner.**
`canonicalTraversalPattern` tries to accept an `ORDER BY`/`LIMIT` tail but does not consume the
arguments, so `RETURN DISTINCT e.name ORDER BY e.name` falls into the projection check and is
refused. There is an orphan comment at `ladybug_icebug_canonical.go:32` describing a
`canonicalTraversalTail` that does not exist in the code, and no test covers `ORDER BY`.

The objective is: fix all three, and leave a test that stops the generated text from drifting
away from the engine again.

## Reasoning and justification of the approach

What ties the three defects together is the same class of risk: **generated instruction that
nobody executes**. The preamble is text the agent reads; the templates are text the agent copies. In
both cases the error is invisible to whoever wrote it, because the artifact is only exercised by
another agent, later, in another session.

So the central fix is not rewriting the examples — it is **closing the validation loop**:

- For the templates, the acceptable validation is executing each one in the MCP. The user
  corrected this explicitly in this session, and the correction is memorized
  (`01M1DGYP5JG0ZNYSVYHDB1M5RK`): reading the parser validates against the source tree, the MCP
  answers for the installed binary and for the real graph, and the two diverge.
- As a complement (not a substitute), a unit test: `internal/ast/rule.go` and
  `internal/ast/ladybug_icebug_canonical.go` are **in the same package `ast`**, so the test
  can extract the query blocks from the generated text and pass each one through
  `parseCanonicalTraversal` — the planner itself validating the planner's documentation.
- For the preamble, the same principle: the hash cache now covers the preamble, so
  propagation stops depending on coincidence.

### The real contract, established by execution in the MCP

The planner's error message delivers the whole contract. For the **8 logical types** —
`CALLS`, `CONTAINS`, `HAS_FIELD`, `HAS_PARAMETER`, `IMPORTS`, `READS_FIELD`, `REFERENCES`,
`WRITES_FIELD` — the **only** accepted form is:

```
MATCH (a)-[:TYPE]->(b) [WHERE ...] RETURN DISTINCT b.property [, b.prop2 ...]
MATCH (a)-[:TYPE]->(b) [WHERE ...] RETURN count([DISTINCT] b.uid)
```

with exactly one end filtered. And the planner is the **only** route for those types —
`WITH`, `UNION`, multiple `MATCH` do not escape it, they are refused with the message that
enumerates the form above.

Forms proved in the MCP in this session (all returned without error):

| Form | Status |
|---|---|
| `MATCH (caller)-[:CALLS]->(t:Function {name:'X'}) RETURN DISTINCT caller.name, caller.path` | ✅ |
| `MATCH (f:Function {name:'X'})-[:CALLS]->(callee) RETURN DISTINCT callee.name, callee.path` | ✅ |
| `MATCH (caller)-[:CALLS*1..3]->(t:Function {name:'X'}) WHERE toLower(caller.name) CONTAINS 'test' RETURN DISTINCT caller.name, caller.path` | ✅ |
| `MATCH (f:File {path:'X'})-[:CONTAINS]->(e:Function) RETURN DISTINCT e.name, e.line_number` | ✅ |
| `MATCH (f:File)-[:IMPORTS]->(m:Module {name:'os'}) RETURN DISTINCT f.path` | ✅ |
| `... RETURN count(caller.uid)` / `count(DISTINCT caller.uid)` | ✅ |

Refused in the MCP (and present in the skill today as an example to follow):

| Form | Refusal |
|---|---|
| `RETURN caller.name, label(caller) AS type, caller.path` | `a label is not projectable here` |
| `RETURN count(caller) AS callers` | `must be DISTINCT` — only `count(caller.uid)` works |
| `RETURN f.name, f.path, count(caller) AS callers ORDER BY ...` | `must project exactly one end` |
| `RETURN m.name, count(f) AS imported_by ORDER BY ...` | `must project exactly one end` |
| `RETURN e.name, e.line_number` (without DISTINCT) | `must be DISTINCT` |
| `RETURN DISTINCT e.name ORDER BY e.name` | `not a plain property projection` — defect 3 |
| `MATCH ... WITH f, count(caller) ... RETURN ...` | `must be a single MATCH ... the planner is the only route` |

And a separate finding: **`IMPLEMENTS` does not exist in this project's graph.** The skill teaches
`MATCH (c:Class)-[:IMPLEMENTS]->(i:Interface ...)` claiming it covers Go interfaces; the
table does not exist and the error lists the labels present. Same for `INHERITS`, to be confirmed.

### Alternatives considered and discarded

- **Fixing only the line 83 template** (the one that errored on me): discarded. The defect is
  systemic, 28 templates project `label()` and 87 omit `DISTINCT`; fixing one leaves the
  others teaching the wrong thing.
- **Writing the lint as regex over the text alone**: discarded. It would reimplement the
  planner's rules in a second place, which is exactly the failure mode that created this bug.
  Calling `parseCanonicalTraversal` is the single source.
- **Leaving `ORDER BY` alone** and rewriting the templates without ordering: discarded. The engine
  clearly intends to accept the tail, the orphan comment proves the intent, and without `ORDER BY`
  half the useful questions ("the most complex ones", "the most called ones") have no form. But
  it is a change to the query engine, so it goes in isolated, with a test, and flagged to the user.

## Findings that only execution in the MCP revealed

Three **silent** defects — none of them errors out, all of them return a plausible and
wrong answer. They were found because the user demanded execution in the MCP instead of reading the
parser, and the unit lint approves all three.

**1. Untyped traversal (`-[r]->`) returns garbage, not an error.** This was the template of the
`🔒 MANDATORY: Before You Edit` block. Executed against `UpsertMandateTrigger`, which has 6 real
callers, it returned 25 rows and **no caller**: the pattern matched the physical
*reverse* tables, so `dependent` came back as `Field`/`Parameter`, `type(r)` leaked the internal name
(`reads_field__function_field_reverse`) and `path` came back absolute. A refusal is visible; this
is not. That is why the lint got a rule of its own and the skill got a 🔒 warning.

**2. Incremental reindex creates a duplicate `File` node with an ABSOLUTE path.** After I edited
`mandate.go`, the graph came to have two `File` nodes for it: `internal/hub/.../mandate.go` and
`/home/you/.../mandate.go`. New entities also came with an absolute `path` without the
leading slash (`home/you/...`), contradicting the skill, which promises path always
relative to the root.

**3. Consequence of 2: a traversal anchored on `File {path: ...}` returns the children of the
WRONG file.** While the duplicate existed, `MATCH (f:File {path: 'internal/hub/adapters/ide/mandate.go'})-[:CONTAINS]->(s:Import)`
returned the imports of `mandate_resume_test.go`, and the same for `Comment`. The equivalent
node-only query (`MATCH (s:Import) WHERE s.path = '...'`) returned the right one, which isolated the
problem to the anchor side. **`graphit_sync` fixed it**: the duplicate disappeared and the traversal
went back to returning the correct 10 imports and 60 comments.

> Honest record of my own near-miss: I was one step away from reporting item 3 as a
> join bug in the canonical planner. It was a dirty index. What separated the two hypotheses was running
> `graphit_sync` and repeating the query — exactly the procedure the mandate describes and that I
> was about to skip.

## System Knowledge

- **`UpsertMandateTrigger` has three fast paths**, and none of them looks at the preamble: (1) the trigger
  hash matches and the file mtime matches → returns without reading the file; (2) the hash matches, the mtime
  does not → reads, reparses the trigger, checks canonical order → returns; (3) no cache → compares
  `m[1] == triggerContent` + canonical order → returns. Zeroing `mandate.hash` does **not** solve it,
  because path (3) also ignores the preamble.
- **`RemoveMandateTrigger` preserves the old preamble literally** — it operates on the
  `inner` read from the file, strips the tag and rewrites. It is a second write path that
  produces an `AGENTS.md` with an old preamble, and it explains the current file's `00:31:25` mtime being
  later than the `00:28:41` `make install` without the text having updated.
- **The 8 logical types have a single route.** It is not only a projection restriction: `WITH`,
  `UNION` and multiple `MATCH` over those types are refused. The planner is the only route,
  so "writing it another way" is not a way out — the question has to fit the form.
- **`count(caller)` is not `count(caller.uid)`.** `canonicalCountPattern` requires an explicit
  `.uid`; `count(var)` falls into the `DISTINCT` rule and is refused.
- **`label()` is forbidden in the projection but allowed in the `WHERE`** of a traversal — the check
  is about the return clause. `MATCH (caller)-[:CALLS]->(t) WHERE (label(t) = 'Function' OR ...)`
  passes.
- **A node-only query is not affected by any of this.** `label(n)` works, `ORDER BY` works,
  aggregation works. The whole restriction is about traversing a logical type.
- **`internal/ast/rule.go` and the planner are the same package `ast`** — which is what makes it possible
  to validate the skill's text by calling the real parser.

### 2026-09-01 — T10 to T13

**T10 — `ORDER BY`/`LIMIT` implemented.** The tail of `canonicalTraversalPattern` came to
consume the ARGUMENTS, not just the keywords — that was what pushed `ORDER BY x` into
the projection and produced the refusal "not a plain property projection", which named the wrong
rule and hid a clause the planner is capable of honouring. The plan gained `orderBy []canonicalOrderKey`,
`limit` and `hasLimit`; `applyCanonicalOrdering` orders the materialized set and truncates.

Design decisions worth recording:

- **The ordering key has to be PROJECTED.** The sort runs over the materialized rows,
  not over the table, so ordering by a column that was not fetched would require widening the projection behind
  the caller's back and hiding the extra column afterwards. A clear refusal, with the fix in the message. An alias
  also serves as a key, and the underlying property resolves to the same column.
- **Numbers compare numerically.** `compareCanonicalValues` handles int/float before falling back to
  string, otherwise `line_number` would order 10 before 9 — which is the bug an ordering
  feature exists to prevent.
- **The canonical key remains the final tie-break**, even with `ORDER BY` present: two
  rows equal on all keys would come back in the order the batched queries produced, which is not
  stable across runs.
- **`ORDER BY` over `count` is refused** instead of ignored: counting returns one row, and silently accepting
  a clause with no effect teaches that it has an effect.
- `TestOrderingDoesNotLoosenTheShapeRule` guarantees that ordering is ADDITIVE: a projected label,

**T11 — root cause of the absolute path, and it was an asymmetry.** `classifyBatch`
(`internal/daemon/syncmodule.go`) normalized the REMOVED path to repo-relative, with the
comment saying the parse cache is keyed that way, and passed the CHANGED path raw, absolute.
`internal/ast/watcher.go` had exactly the same asymmetry — two independent callers with
the same defect, which decided where the fix belongs: in the pipeline.

The full mechanism: `absToRel` was built with `filepath.Abs(rel)`, which resolves against the
**process working directory**. In the CLI the CWD is the project root and everything coincides. In the daemon
it is not — and the daemon serves several projects, so it cannot chdir into any of them. With
absolute `ChangedPaths`, `filepath.Abs(abs) == abs`, so the map pointed absolute to
absolute, `correctRelPath` became the absolute path itself, and
`r.pf.Path = filepath.Join(abs, correctRelPath)` produced a DUPLICATED path. Hence the two
observations of the first round: absolute `File.path`, and an entity with `home/you/...` without a
leading slash, which is `writer.rel` of the duplicated path.

Fix: `repoRelativePaths(root, paths)` normalizes either of the two forms against the ROOT,
never via `filepath.Abs`. What is READ became always `filepath.Join(abs, rel)` and only what
is STORED is relative. Good side effect: `fileHashes` is now keyed absolutely and the
later lookup hits, where before it missed and recomputed the SHA-256 of every file in the batch.
A path outside the root passes through intact — it has no relative form, and rewriting would invent a file.
